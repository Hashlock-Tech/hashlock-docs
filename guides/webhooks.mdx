The [maker feed](/guides/maker-feed) tells you what to quote. Events tell you what happened to your account: quotes, counter-prices, messages and swap steps. The swap statuses `expired`, `failed` and `refunding` send no event, so read `GET /v1/swaps/{id}` for those. A webhook pushes each event to your URL. `GET /v1/events` returns the same events when you ask, with no URL to host. See [Read events without a URL](#read-events-without-a-url).

## Register

```bash
curl -s -X POST $HL/v1/webhooks -H "Authorization: Bearer $HK" \
  -H "content-type: application/json" \
  -d '{ "url": "https://example.com/hashlock", "events": ["swap.funded", "swap.settled"] }'
```

Response (`201`): `{ "webhook": { id, url, events, enabled }, "secret": "whsec_…" }`. **The secret is shown once.** Store it; you need it to verify deliveries.

- `url` must be `https`. A non-public address literal is rejected at registration. A hostname that resolves into a private range registers, but every delivery to it fails (visible only as `lastStatus`).
- Omit `events`, or send an empty list, to receive all events.
- An account holds at most 10 webhooks. An 11th registration answers `409`.

Other calls: `GET /v1/webhooks` (list, secret not shown), `DELETE /v1/webhooks/{id}`, `POST /v1/webhooks/{id}/ping` (sends a test `ping` delivery once, without retries, and returns `{ ok, deliveryId }`).

## Events

Each event goes to the account it concerns. `quote.created`, `swap.*` and `secret.revealed` go to both parties. `rfq.expired` goes to the RFQ's creator. The other thread events go to the counterparty of whoever acted. When the RFQ itself closes, `thread.closed` goes to the maker of each thread that was still open; when it reopens, `thread.reopened` goes to the maker of each thread it closed.

| Event | When | Payload fields |
|---|---|---|
| `quote.created` | A maker quoted an RFQ. | `rfqId`, `threadId`, `quoteAmount` |
| `proposal.created` | The counterparty proposed a new price. | `rfqId`, `threadId`, `amount` |
| `terms.accepted` | The counterparty accepted your price or the terms. Read the thread to see whether your accept is still needed. | `rfqId`, `threadId`, `amount` |
| `message.created` | The counterparty sent a chat message. Read it with `GET /v1/threads/{id}`. | `rfqId`, `threadId` |
| `rfq.expired` | Your RFQ expired. | `rfqId` |
| `thread.closed` | A negotiation of yours ended without a deal. The counterparty declined it, or the RFQ was cancelled, expired, deleted or agreed with another maker. After a decline or a deleted RFQ, the thread is gone (`404`). | `rfqId`, `threadId` |
| `thread.reopened` | The RFQ was reopened, and your closed negotiation with it. | `rfqId`, `threadId` |
| `swap.agreed` | Both sides accepted; the swap exists (status `agreed`). | `swapId`, `threadId`, `status` |
| `swap.funded` | A leg was funded (status `initiator_funded` or `counterparty_funded`). | `swapId`, `status` |
| `secret.revealed` | The initiator claimed; the secret is public (status `initiator_claimed`). | `swapId`, `status` |
| `swap.settled` | The counterparty's claim landed (status `counterparty_claimed`). Read the swap to see each leg. | `swapId`, `status` |
| `swap.refunded` | A leg was refunded (status `refunded`). | `swapId`, `status` |
| `swap.half_settled` | One leg was claimed and the other refunded at its timelock (status `half_settled`). | `swapId`, `status` |
| `ping` | Sent by `POST /v1/webhooks/{id}/ping`. | `message` |

`amount` and `quoteAmount` are in base units. Payloads carry ids only: fetch the detail from `GET /v1/threads/{id}`, `GET /v1/rfqs/{id}` or `GET /v1/swaps/{id}`.

Every body also has `type` (the event name), `createdAt` and `deliveryId`. The body of a recorded event also has `id`. Its `id` and `createdAt` are the event's own: `GET /v1/events` returns the same `id` for it. Dedupe on `id` across webhooks and `GET /v1/events`. A body without `id` is a `ping` or an event that the server failed to record, and its `createdAt` is the delivery time.

- The same event can arrive twice. A delivery is dropped once its [retries](#retries-are-best-effort) run out.
- Events can arrive in any order. Deliveries run in parallel, and a retried one can arrive hours after later events.
- Events are notifications, not the record. The thread and the swap are the record: read them before you act, and when something looks missing.

New event types are added over time. Handle an unknown `type` by returning `2xx`, not an error.

## Delivery

Each delivery is a `POST` with a JSON body and these headers:

| Header | Value |
|---|---|
| `content-type` | `application/json` |
| `user-agent` | `Hashlock-Webhooks/1` |
| `x-hashlock-event` | the event name |
| `x-hashlock-delivery` | the delivery id |
| `x-hashlock-timestamp` | Unix time in seconds, as a string |
| `x-hashlock-signature` | `sha256=<hex>` |

Delivery does not follow redirects and times out after 10 seconds.

## Verify the signature

The signature is `HMAC-SHA256(secret, "<timestamp>.<body>")`, hex-encoded, where:

- `secret` is the full `whsec_…` string from registration, used as the HMAC key as-is;
- `timestamp` is the `x-hashlock-timestamp` header;
- `body` is the **raw** request body, byte for byte. Do not re-serialize parsed JSON.

```typescript
import { createHmac, timingSafeEqual } from 'node:crypto';
import express from 'express';

const SECRET = process.env.HASHLOCK_WEBHOOK_SECRET!; // "whsec_…"
const app = express();

app.post('/hashlock', express.raw({ type: 'application/json' }), (req, res) => {
  const ts = req.header('x-hashlock-timestamp') ?? '';
  const sig = req.header('x-hashlock-signature') ?? '';
  const body = (req.body as Buffer).toString('utf8');

  const expected = 'sha256=' + createHmac('sha256', SECRET).update(`${ts}.${body}`).digest('hex');
  const ok = sig.length === expected.length && timingSafeEqual(Buffer.from(sig), Buffer.from(expected));
  if (!ok) return res.status(401).end();

  // Replay protection: reject timestamps older than your own tolerance.
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return res.status(401).end();

  const event = JSON.parse(body);
  // handle event.type …
  res.status(204).end();
});
```

The 300-second window above is an example value for your receiver, not a server setting.

## Retries are best-effort

A non-`2xx` or a timeout is retried after 15 s, 1 m, 5 m, 15 m, 1 h and 2 h — **7 attempts over at least 3 h 21 m** — and then dropped. There is no redelivery endpoint and no delivery log beyond `lastStatus` (and `lastDeliveryAt`) on `GET /v1/webhooks`.

If your receiver is down longer than that, you lose deliveries. To catch up, pass a `cursor` you kept from an earlier `GET /v1/events` call as `after`. A webhook `id` is not a cursor. A call without `after` returns only the newest page. Without a kept cursor, start from `after=0` and page on with the returned `cursor` to read every kept event (30 days), and skip the ids you already handled. Then read `GET /v1/swaps/{id}` and `GET /v1/threads/{id}` for each open deal: they are the record, and some changes send no event.

## Read events without a URL

`GET /v1/events` returns the events of your account, oldest first. It needs no URL and no registration, and it lists every event type whatever your webhooks subscribe to.

```bash
curl -s "$HL/v1/events?after=$CURSOR" -H "Authorization: Bearer $HK"
```

Response: `{ "events": [ { id, type, createdAt, … } ], "cursor": "…" }`. Each event has the payload fields from the [table above](#events).

- Keep the returned `cursor` and pass it unchanged as `after` on the next call. Pass it also when `events` is empty: the cursor never skips a recorded event. Events are kept 30 days, so a cursor older than that can pass events that were deleted; then reconcile from the threads and swaps.
- Without `after`, you get only the newest page. `after=0` reads every kept event from the oldest. Call once to start, then always with the returned `cursor`.
- `limit` sets the page size, 1 to 200 (default 100). With `after`, fewer than `limit` events means you are caught up.
- An event appears here within about a second of being recorded. Events are kept 30 days.
- The rules above hold here too. Dedupe on `id`, expect events out of order, and read the thread or the swap before you act.
